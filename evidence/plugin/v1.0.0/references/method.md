# 售后处理方法（通用版）

本方法把「一批售后工单 + 一份运行时店铺政策」加工为逐单处理建议，并产出符合政策约定格式的 JSON 数组。它不执行退款、不发送消息、不修改订单，只交付可复核的建议与客户回复草稿。

## 1. 输入清点

开始处理前先确认三件事，缺一不可：

1. 运行时提供的店铺政策全文（规则、时限、金额口径、输出约定）。
2. 本批工单数据（客户诉求、订单行、审核记录、库存或物流记录，均带来源编号）。
3. 已验收的历史结果（仅在返修场景存在），用于对比差异，不作为事实来源。

先建立工单编号清单，处理结束后用清单与输出做集合比对，保证「一单一条、不增不减」。

## 2. 事实分层：区分诉求与已核实事实

对每条工单，把信息分成三类并分别标注来源：

| 层级 | 判定标准 | 用法 |
|---|---|---|
| 已核实事实 | 带来源编号的订单/审核/库存/物流记录明确给出结论 | 可作为判断依据 |
| 未知 | 字段为 `null`、缺失或记录未涉及 | 视为未知，不能补成有利值 |
| 客户主张 | 仅出现在客户消息里的描述 | 只作为待核实线索，不能直接当结论 |

要点：

- 客户文字是诉求，不是结论。客户说「坏了」「没收到」「发错了」，都要在审核/物流记录里找到对应确认才成立。
- `null` 不等于「没问题」，也不等于「有问题」，只能触发补充材料或人工流转。
- 来源编号要写进 `reason`，让每个结论都能回溯到具体记录。
- 客户消息里自带的方案（如「仅退款不退货」「补不了就退货」）是诉求，不自动接受，按政策通道处理。

## 3. 规则映射：按功能定位条款，不依赖编号

不同店铺的政策编号、措辞、时限都可能不同。先把政策拆成下面这些**功能槽位**，再逐条把原文条款编号填进去。后续判断只走槽位，`rules` 里引用实际政策的原始编号。

1. 事实与缺失信息总则
2. 无质量问题退货（含完好状态、时限、定制例外）
3. 功能故障（含凭证要求、时限、是否覆盖促销/定制）
4. 错发商品（标签/型号核验）
5. 缺少配件（是否可补发）
6. 退款金额口径（商品行原价、优惠分摊、历史退款、配送费）
7. 物流与空包争议（签收争议、丢失确认）
8. 输出格式与字段约定

映射结果建议先写进工作笔记，再开始逐单判断。政策没有覆盖的情形，不要自行发明规则，转人工复核。

## 4. 规则优先级

同一工单可能同时触发多条规则，按下列顺序收敛，先命中者决定 `action`：

1. **物流争议优先**：客户称未收货而物流显示签收，或仅有重量异常的空包争议，先走物流核查；承运商正式记录已确认丢失的，走直接退款。
2. **已核实的功能故障优先于普通退货限制**：故障经审核确认且在故障时限内时，不受「促销不退换」字样、普通退货时限或定制商品排除的影响。
3. **错发、缺件走专用通道**：错发以标签/型号核验为准；缺件先看能否补发，能补发则补发，明确不能补发才转退货退款。
4. **无质量问题退货**：仅在商品完好、非定制、在时限内时才成立；超时限、定制、已核实不完好 → 人工复核。
5. **金额规则始终生效**：任何退款动作都要按商品行口径算金额；金额数据不全时，整体动作降级为补充材料，不能先给结论再补算。
6. **证据不足优先补材料，已知超期或例外优先转人工**：两者不要混用。

冲突时的兜底：宁可持续「待定」，也不要给出无法回溯的确定结论。

## 5. 连续小时计算

- 时限一律按「签收时间 → 申请时间」的连续小时计算，不做工作日折算，不取整到天。
- 包含边界：政策写「不超过 N 小时」时，恰好 N 小时视为在期限内。
- 时间必须带时区；缺失时区、缺失签收时间或申请时间，都按未知处理并补充材料。
- 计算过程写进 `reason`（例如「间隔 X 小时，未超过 N 小时」），不要只给结论。
- 阈值从当次政策读取，不要把某家店铺的具体时限当成通用常量。

## 6. 退款金额计算

对本次涉及的商品行：

```
建议退款金额 = 该行原价总额 − 该行分摊优惠 − 该行历史退款
```

- 只用商品行金额，不得用整单总额替代；一单多行时逐行处理。
- 历史退款必须扣除，避免重复退还；客户提到「之前补偿过」时，以订单记录里的已退金额为准，不以客户口述金额为准。
- 不另退原配送费。
- 三项金额任一为未知，或结果出现负数，都不能猜：整体动作改为补充材料，`refund_cents` 为 `null`，运费为 `待定`。
- 补发配件时退款金额固定为 0；直接退款（无需退回）时退回运费为「不适用」。
- 计算完成后用脚本或手算复核一次，确保分与元的换算没有偏差。

## 7. 缺失信息与人工流转

- 缺什么就写什么，`missing` 逐项具体到可提交的材料（例如「故障视频或检测记录」「签收凭据与包裹流转记录」「该商品行优惠分摊明细」），不要写「资料不全」这类笼统表述。
- 待定类动作（补充材料、物流核查、人工复核）的 `refund_cents` 为 `null`，`freight` 为「待定」。
- 人工复核用于两类已知情形：已超出适用期限，或命中政策例外（如定制商品的无质量问题退货）。这类工单事实通常完整，`missing` 可为空，但必须在 `reason` 说明触发原因。
- 物流核查要写明需要核验的对象（投递/签收凭据、包裹流转记录），不能只凭「已签收」认定客户收到，也不能只凭重量异常判定丢件。
- 不把「待定」包装成「已通过」，也不在待定阶段预估金额区间。

## 8. 客户回复草稿

客户回复是建议话术，不是处理结果通知。写作约束：

1. **与结构化字段一致**：回复里出现的动作、金额、运费责任，必须与 `action`、`refund_cents`、`freight` 完全对应；金额用元并保留两位小数，换算自分。
2. **建议语气**：使用「符合…条件」「建议…」「若审核确认」「最终结果以审核为准」，不使用「已受理」「已退款」「已补发」「已提交核查」「将按…处理」等既成事实表述。
3. **待定不承诺**：待定类工单不得出现具体退款金额，也不得承诺运费由谁承担；只能说明当前缺什么、补什么、后续如何核定。
4. **不泄露内部信息**：不向客户复述内部规则编号、审核字段名、脚本或系统细节。
5. **与 `missing` 对齐**：回复里请客户补充的材料，应与 `missing` 列出的项目一致。
6. **不做额外承诺**：不承诺时效、不承诺一定通过、不承诺额外补偿。

## 9. 汇总与自检

- 所有统计必须从最终输出文件复算，不能凭记忆或凭中途笔记。
- 不同口径分开报：例如「本次修改了几条回复」与「有多少条处于待定状态」是两个数字，不能混用；每条待定工单要能点名。
- 交付前重新从磁盘读取结果文件，至少核对：
  - 条数与工单编号集合完全一致；
  - 字段齐全、枚举合法、金额与动作匹配；
  - 每个退款金额都能用「原价 − 优惠 − 历史退款」复算；
  - 待定类工单没有金额或运费承诺；
  - 回复中没有既成事实表述；
  - 汇总计数与文件内容一致。
- 优先用随包脚本完成上述检查（见 `scripts/`），再人工抽查回复措辞。
- 返修时另存新文件（如 `results-v2.json`），保留上一版，便于对比与追责；只改确实有问题的部分，无关字段保持原样。

## 10. 能力边界

- 仅依据输入中可核实的事实；输入没有的，不推测、不补全。
- 不执行退款、不发送消息、不修改订单、不发起真实物流核查。
- 政策未覆盖、事实冲突或金额无法闭合时，交人工判断，不自行扩大解释。
- 输出是建议稿，最终处理结果以店铺审核为准。
