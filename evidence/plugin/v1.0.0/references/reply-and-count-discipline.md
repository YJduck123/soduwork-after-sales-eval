# 回复与计数纪律

本文件记录三类容易被人工验收打回的问题，以及通用写法。要点与具体订单、金额无关，可迁移到任何店铺政策。

## 一、客户回复必须与结构化结果一致

结构化字段是唯一事实源，回复只是它的客户化表达。常见不一致：

| 结构化状态 | 错误回复 | 正确方向 |
|---|---|---|
| 运费为「待定」 | 「退回运费由商家承担」 | 「运费需在材料补齐并审核后确定」 |
| 金额为 null | 「可退 199.00 元」 | 「暂无法计算退款金额，需补充…」 |
| 动作为补充材料 | 「已为您安排退款」 | 「请补充…，收到后继续审核」 |
| 动作为物流核查 | 「退款会尽快到账」 | 「核查期间无法确认金额与运费」 |

自检方法：把每条回复里的金额、运费责任、动作抽出来，逐项与 `refund_cents`、`freight`、`action` 对照；任何一项对不上就改回复，不改字段。金额表达统一用元、两位小数，由分换算而来。

特别注意「预期结果」：补充材料后可能适用某条规则、可能由商家承担运费，都只是预期，不能提前写进回复。回复只描述当前状态和下一步。

## 二、建议不能冒充已执行

处理建议不等于处理动作。以下表达都构成越界：

- 已受理、已通过、已退款、已补发、已提交核查、已发起、已安排、已完成
- 「将按…处理」「我们会为您补发」等承诺式表述
- 「复核结果会另行通知」——暗示流程已启动

推荐表达：

- 符合…条件，建议…
- 若审核确认，可按…处理
- 目前无法确认…，需补充…
- 是否受理及结论将另行告知
- 最终结果以审核为准

对客户只承诺「会据此继续审核」是安全的，因为审核本身是本流程的一部分；但不能承诺审核结果。

## 三、汇总计数必须可复算

统计口径要分开、来源要唯一：

1. 先固定统计对象：本次输出的最终文件，而不是中途草稿或修改记录。
2. 分开报不同维度，例如「修改了客户回复的条数」与「处于待定状态的条数」是两件事，不能相加、不能互相替代。
3. 待定类要能逐条点名，而不是只给一个总数。
4. 每个数字都要能从文件复算：动作分布用脚本统计，待定清单用筛选结果列出。
5. 报告写完后，重新读一次文件再核一遍数字；发现不一致，以文件为准改报告，不改文件去凑数字。

建议直接使用随包脚本：

```
python scripts/check_results.py --results results.json --tickets tickets.json --summary-out summary.json
```

脚本会输出总数、动作分布和待定清单，并做结构、金额、回复一致性检查。
